# Development-only thumbnail renderer (UI2)

This is a separate disposable browser image, not a new process in the Runner or the user preview. Do not enable the feature in production from this source patch. There are no database migrations and no user-generated Docker commands.

## Runtime contract

- Build the image on the Ubuntu development VM from an operator-verified digest-pinned Python slim Bookworm base (pass `BASE_IMAGE=python:3.12-slim-bookworm@sha256:<verified digest>`). The build installs Chromium, fonts and Playwright 1.57.0. APT package versions are not independently pinned by this V1 Dockerfile; review and record the resulting image ID and dependency versions before promotion.
- Load the reviewed image into the **dedicated ZoeBuild UID 1001 rootless execution daemon**, not the system or ZoeLearning daemon. Use the exact local `sha256:...` image ID in `ZOEBUILD_THUMBNAIL_RENDERER_IMAGE_ID`. The Runner does not pull images. No Docker socket, host filesystem bind, network namespace sharing, project workspace mount or service credentials are allowed in this browser container.
- The renderer alone uses the pinned seccomp JSON in `src/services/build/thumbnailSeccompProfile.ts`, derived from the Docker 29.5.3 upstream default profile and verified in the isolated VM fixture. The SHA-256 of the exact JSON sent to Docker is `2d5a038bdb9482390782c912233e30e80ebf3b7dd7bb37f25e1d3e1b283ba487`. No runtime network download or configurable profile override is used. Capture fails closed on an unvalidated engine release or architecture; revalidate before engine upgrades.
- Chromium's own sandbox is enabled. The container also has network none, a read-only root, dropped capabilities, no-new-privileges, PID/memory/CPU limits, temporary storage and an alarm/deadline. Do not weaken these settings if nested Chromium sandbox support fails. Verify the dedicated daemon can run the browser with these exact constraints before enabling the feature.
- The renderer can request only bounded GET resources from an already-running, owner-bound, exact-revision TanStack development preview. The Runner resolves the existing private lease and uses its normal read fence for every resource, then checks the lease again before accepting the JPEG. No RPC mutations, external requests, arbitrary origin, platform cookies, HMR tickets or browser credentials are relayed. The worker is single-flight and has no persistent data. It is marked for the existing dedicated Runner startup cleanup if an abnormal exit leaves a resource behind.
- First successful screenshot for a saved revision is immutable and private in the existing media R2 bucket under `project-thumbnails/<owner-sha256>/<project>/<version>/homepage-v1`. Ensure credentials permit this namespace and configure a prefix-scoped retention policy before broad rollout; old versions/deleted project bytes are not automatically purged by this patch. They are not served after ownership/archive/revision checks fail. There is no new public bucket, URL signing, or schema change.

- Protocol v2 requires the exact image label `com.zoeskoul.thumbnail-renderer.version=3`. The asynchronous renderer emits `ready` and awaits `start` before launching Chromium. Requests remain single-flight per renderer; no multiplexing, larger CPU/memory budget, or extended capture deadline. The Runner rejects v1 and v2 images, and requires verified container absence before returning success or releasing the capture slot.

The v3 relay requires a two-value `accept` field on every GET: `text/css` for browser stylesheet resources and `*/*` otherwise (including CSS imported as JavaScript). A local stylesheet response with a non-CSS MIME type fails the capture rather than caching an unstyled screenshot. Network isolation and owner/revision checks are unchanged. Existing cached thumbnails can be replaced through the explicit refresh action after v3 activation; no cache is deleted by this change.

## Acceptance before enablement

1. Compile/test the shared build contracts and build application package and both apps. Inspect the actual execution-pool middleware, Runner client request/response limits and gateway timeouts; these files were not present in the supplied source export.
2. Build the separate browser image; run the fixture test with the exact non-root, no-network, read-only sandbox constraints on the development VM. The included Python fixture requires Playwright, Chromium and Pillow in its test environment; it is not invoked by the application. The browser container's startup, Docker attach relay, resource limits and cleanup must also be verified end-to-end with a test project.
3. Rebuild/align only the development ZoeBuild Runner from the validated source revision using the existing controlled replacement and rollback procedure. Do not replace the Learning Runner or publishing containers.
4. Only after isolation and cleanup pass: set `ZOEBUILD_PROJECT_THUMBNAILS_ENABLED=true` for the ZoeBuild Runner and editor server, and `NEXT_PUBLIC_ZOEBUILD_PROJECT_THUMBNAILS_ENABLED=true` for the editor client build/dev launcher. Set the verified renderer image ID on the Runner. Both feature gates default off. Keep them off in production.
5. Open a test TanStack project, allow its live preview to become ready and remain on a saved revision for 12 seconds. The browser posts a bounded revision-only capture request. Confirm HTTP 200 and a 1280×720 JPEG thumbnail on return to Projects. On a new saved revision, confirm a separate cached thumbnail. Dashboard reads must not create preview containers. Check that unauthorized, archived and stale revision reads fail; record preview/HMR latency with and without capture. Verify browser cleanup and rollback before proceeding to other projects.

V1 does not automatically start old projects for bulk backfill, force-recapture an unchanged revision, or capture immutable fallback/legacy stack previews. It intentionally leaves the card placeholder on a cache miss or failure. External resources and application RPCs are not included. JPEG is used because Chromium/Playwright produces it natively, with a 512 KiB bound. These restrictions should be revisited only with explicit runtime evidence and reviewed policy.
